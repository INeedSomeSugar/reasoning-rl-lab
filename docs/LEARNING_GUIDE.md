# 从可运行代码理解小模型后训练

先读 `HANDOFF.md` 的已完成证据，再按本文件走代码。只把真实运行结果用于面试，不把计划写成成果。

## 1. SFT 到底学什么

给定题目prompt x与标准解y，最小化：

\[
L_{SFT}=-\frac{1}{|y|}\sum_{t\in y}\log \pi_\theta(y_t\mid x,y_{<t}).
\]

`modeling.encode_sft` 拼接 prompt 与完整解答；prompt标签为-100，completion保留token ID。`CompletionCollator` 在右侧补padding，并把padding标签也设-100。CausalLM内部把logits与labels错开一位，不能再次手工shift。训练代码入口是 `training.run_sft` 的 `MaskedTrainer.compute_loss`，token统计与真正监督的位置分开计数。

为什么过长样本整条丢弃？直接截断可能只留下推理开头、丢掉最终答案，改变训练目标；这里记录被丢弃ID，正式对照报告长度过滤造成的分布偏差。训练loss下降只表明更拟合这些解答，不证明验证或测试正确率提高。

## 2. LoRA 更新哪些参数

对冻结线性层W加入低秩更新：`W' = W + (alpha/r) * B @ A`。本项目rank=8、alpha=16、q_proj/v_proj，只有LoRA矩阵可训练。初始化一般使更新为0；第一次反向某个因子梯度为0并不代表整个LoRA失效，要检查总梯度和实际参数delta。

入口：`modeling.load_model` 中的PEFT配置；`training.check_model` 检查forward loss有限、可训练参数有非零有限梯度、冻结参数无梯度、AdamW后adapter确实改变、save/reload logits在明确容差内一致。

NF4冻结骨干权重以降低显存，训练的是LoRA，不是直接更新4-bit整模型。PEFT会调整非量化层精度，推理重载也必须采用同样协议。NVIDIA能跑不代表AMD同一量化库能跑；台式机首轮使用非量化FP16。

## 3. GRPO 如何利用多个答案

同一题生成G个解答，二值奖励r_i，计算：

\[
A_i=(r_i-\bar r)/(s_r+10^{-4}),\quad
\rho_{i,t}=\exp(\log\pi_\theta(o_{i,t})-\log\pi_{old}(o_{i,t})).
\]

目标中的策略项为 `min(rho*A, clip(rho,1-eps,1+eps)*A)`，再按选定的GRPO token/sequence归一化求平均。组内全对或全错时A全0，所以“奖励很高但梯度为0”完全可能。

若每次解答独立且成功率为p，则组内出现正负混合奖励的概率为 `1-p^G-(1-p)^G`。G=2时等于 `2p(1-p)`，这也说明了中等成功率题的作用。实际推理样本及其有限次数估计会有噪声。本机最初4步、G=2确实出现100%零方差，适配器delta=0，随后才扩大G和题池进行信号预实验；不能把这次零loss写成学习成功。

`scoring.group_advantages` 是可读参考实现与测试；真正训练的group advantages、ratio和loss位于固定版本 `trl/trainer/grpo_trainer.py` 的 `_generate_and_score_completions` 与 `_compute_loss`。本项目只在生成边界接入采样，不重写优化公式。已保存官方源快照 `docs/sources/grpo_trainer_v0231.py` 供阅读，不把它当运行依赖或自行维护的框架。

显式选择 `loss_type=grpo`、group标准差归一化、beta=0、epsilon=0.2、单轮更新。TRL0.23.1默认loss_type为dapo；不显式记录就可能把库默认误认为论文设置。本机beta=0节省参考模型开销，也意味着没有KL约束；这是清楚的取舍，不是原论文逐项复现。

## 4. 奖励为什么分正确与格式

`scoring.score_answer` 仅解析明确的最终数值，Decimal/Fraction精确比较。`#### 7`可以格式正确但答案错误；`\\boxed{6}`可以答案正确但不满足本项目####格式。奖励只使用正确性0/1，格式单独统计，防止通过练格式制造“推理提升”。

解析器错误也会造成假阴性，所以原始输出、提取方法和gold都保留。本机验证时确实发现模型写成 `####` 后另起一行 `**Answer:** 864`：数值正确但严格格式不合规。v2接受最终答案区域内唯一数值并单独统计格式，在验证集离线重评分，保留原记录；不调整保留集的评分规则。截断样本的梯度mask与错误率另列，不能把模型输出了答案之后继续重复导致的截断悄悄删出评测分母。

早期日志的 `frozen_parameters` 是直接对存储张量做 `numel()` 求和；4-bit权重已压缩，不能拿这个调试字段当逻辑参数总量或计算模型规模占比。公开模型名沿用Qwen3-1.7B，可训练LoRA参数实测为1,605,632个。

## 5. 难度感知采样在做什么

训练题i生成K次，估计 `p_i=(s_i+0.5)/(K+1)`。分数 `g(p)=4p(1-p)` 在p=0.5达到峰值；混合均匀采样：

\[
q_i=u/N+(1-u)\,g(p_i)/\sum_jg(p_j),\quad u=0.25.
\]

直觉：总是做对的题可能信号少，总是做错的题可能暂时太难，优先选择部分能做对的题以产生组内差异。它不保证一定更好：估计有噪声、零方差取决于G，探测也耗预算。

入口 `sampling.DifficultySampler`：先验、权重、独立RNG、刷新与覆盖诊断都可单独查看。`training.InstrumentedGRPO._generate_and_score_completions` 先按固定规则刷新，再抽题，展开成连续G个同题样本后交给TRL。奖励函数再次验证每组ID一致，防止把不同题混在同一优势归一化组。

D动态刷新，E只用初始成功率。若D与E相近而都优于C，可能主要是初始分布作用；若D超过E，要结合实际曝光、成本与多种子排除噪声。没有提升时，应检查探测是否把预算花完、题目是否都落在p接近0/1、输出是否普遍截断。

K=2时p只有少数离散值，刷新造成的权重变化也可能主要来自Monte Carlo噪声，不能仅凭“权重变了”断言模型能力变化。正式实验应同时看探测不确定性、刷新成本与真实奖励/独立正确率。

具体说，K=2、先验0.5时，p只有1/6、1/2、5/6三档，g只有5/9和1两档。混入均匀项前最大权重比也只有1.8；这是一种温和、低分辨率的采样启发式。扩大K能提高估计分辨率，却增加探测开销。因此要用实际“混合奖励组数/累计总秒数”检查探测是否值得，而不是只展示权重热图。

这里的难度是“模型在当前提示、精度、解码预算和评分器下得到可接受最终答案的成功率”，不等于题目的固有数学复杂度。空答案、重复和截断也会降低p；若采样主要利用这些输出差异，不能解释成更会数学推理。32题扩大SFT评测确实出现格式更好、正确率更低的情况，见reports/error_analysis.md。

## 6. 为什么不能只对齐训练步数

D多了真实模型的K次全池探测。同一步数时D可能花更多计算；正确问题是同一端到端时间内C/D分别能达到什么表现。共同SFT单列；探测、验证、训练输入/输出token及GPU时间均保存。token不是等价FLOPs，长度、batch和KV cache都会影响成本。

`runtime.Ledger` 记录阶段wall/device elapsed/峰值显存；`budget_progress`记录累计成本；`reporting.compare_runs` 核对共同SFT哈希、同一池、同一协议和硬件，生成实际观测点图。不同硬件耗时分开，不用3060秒数直接折算9070XT或4090。

预算早停时也要检查库输出的吞吐分母。Transformers4.57.1的Trainer用`self.state.max_steps`传给最终`speed_metrics`；本轮配置100000步上限、实际按时间停止，均匀组完成21步/约1148.61秒，原始库日志仍给出87.079 steps/s。后者基于计划上限，不是真实速度；项目汇总使用实际完成步数或真实token除以实测时间，保留原日志供核对。包含验证的端到端速度也不能当成纯生成kernel吞吐。

## 7. 误差分析怎样有依据

真实案例：TRL准备GRPO时会对embedding/lm_head再次转换精度，独立加载器与训练上下文的输出可能不同；仅看YAML中的BF16不能证明所有层精度一致。`reports/trl_precision_audit.json`保存了实际转换前后的dtype。比较终点要重新走共同加载器，训练内验证另标为诊断。

另一个案例：首轮静态组8步的平均GRPO loss约9.31e-10，但LoRA delta L2约0.007587且有12个非零优势。组内中心化优势可能使标量损失接近0，梯度向量仍可非零；应联合检查优势、梯度和参数变化。均匀组最初G=2的delta=0则是真正没有更新，二者不能混淆。

先看原始预测，分清格式、提取失败、重复与截断，再人工核对算术错误、遗漏条件、错误建模。自动标签的 `wrong_numeric_answer_requires_review` 不等于已确认算术错。把“没有理解题意”和“最后一步乘法算错”分开，才能判断应该改训练数据、生成预算还是评分器。

所有保留评测题只在冻结后使用。验证集可开发，但反复查看会产生适配，必须保留最终独立测试。公开基准可能进入预训练，当前无法证明没有污染。

本项目还发现真实训练标签疑义：`gsm8k-train-05134`把“比Ann少15%”倒用为Ann=Jared×1.15。按字面应除以0.85，且会得到非整数辆数，不能擅自写出新的整数gold。旧轮次保留官方参考与实际奖励；新NF4/eager轮次在任何C/D/E前共同排除，记录原ID和原因。这说明可验证奖励只保证与给定gold一致，gold本身仍可能有问题。该审阅由辅助分析完成，`human_reviewed=False`，并非完整数据集质量结论。

## 8. 运行失败如何保留训练证据

CUDA非法内存访问可能让当前进程后续保存失败；堆栈中的算子位置也不等于根因。`training._evaluate_with_recovery`在诊断生成前保存带step的适配器和哈希，再启动验证。真实NF4/eager smoke中，恢复适配器与最终适配器字节相同；工程检查还注入验证失败，确认已保存权重保留。它没有优化器状态，不能承诺精确续训。

完整BF16/eager曾通过前后向和SFT，但较长G4生成在6GB显存接近满载时停滞。这与“模型权重加载成功”是不同层次的验证。NF4/eager随后完成短GRPO，只证明当前链路能运行；另建A/B与新前缀，避免把后端数值变化混成算法收益。相关记录见`reports/runtime_incidents.md`。
